# V23 尺度修正 MoE：三数据集、多种子与机制消融

制定日期：2026-09-09。运行预算：单 GPU0，目标北京时间 2026-09-10 09:00 前结束。当前仅完成流程测试与测时，尚未启动正式队列。

## 1. 要回答什么

1. 过去的改善是否主要来自 0.01 分支监督，而非新结构？
2. 在相同分支监督下，共享细预测的有界残差参数化是否优于原独立尺度预测？
3. 新模型中，分支监督、补全动态路由、可学习区域聚合分别是否有价值？默认残差上限是否过紧？

所有候选预先定义，不根据测试集结果自动选方案或调整超参数。训练中按验证集 MAE 选择 checkpoint，测试集仅在每次训练结束后评价最佳 checkpoint 一次。

## 2. 实验矩阵：78 次完整训练流程

每个方案都覆盖 TaxiBJ、BikeNYC、CHAP 的 fixed/random，缺失率固定 0.4，即六个条件。

| 代号 | 方案 | 种子 | 次数 | 对比对象及目的 |
|---|---|---|---:|---|
| B00 | 原 A01，分支监督权重 0 | 42 / 2026 / 3407 | 18 | 当前代码中保留的原模型参照 |
| B01 | 原 A01，分支监督权重 0.01 | 42 / 2026 / 3407 | 18 | 对 B00：分离监督带来的改善 |
| N01 | 新模型，分支监督 0.01，有界修正上限 1 | 42 / 2026 / 3407 | 18 | 对 B01：评价新参数化；对 B00：总体变化 |
| N00 | N01 去掉分支监督 | 42 | 6 | 对 N01：新结构下监督是否仍必要 |
| NU | N01 补全权重改成均匀融合 | 42 | 6 | 对 N01：后端动态 MoE 是否必要 |
| NG | N01 改为规则观测归一化聚合 | 42 | 6 | 对 N01：复杂聚合的性能/成本收益 |
| NB2 | N01 残差上限从 1 改为 2 | 42 | 6 | 对 N01：检查是否受过紧边界限制 |

这里 B00 不是之前的 A00：B00 的后端仍然是 learned 路由；所有方案前端均关闭动态门控。B00/B01 使用三个可学习聚合器，均匀融合，不是固定规则区域。

N01 与 B01 的区别包含共享细预测、残差输出解释及修正头零初始化，属于整体参数化对照，不能仅归因于 tanh 限幅。NB2 是边界敏感性检查，不是“有界对无界”的完整消融。

NG 不仅改变形状，还改变聚合器数量、粗节点数和参数量，且不适用原可学习分配的正则项；因此是**替代架构的效果/成本比较，不是等容量纯几何消融**。测时文件记录各方案训练参数量。

## 3. 统一训练策略

- 120 epoch、每 2 epoch 完整验证一次，无提前停止。
- batch_size=4、seed 如上、学习率 0.001、cosine、AMP、梯度裁剪 1、CPU 线程 2。
- **训练集最多均匀抽取 512 个窗口，并非三个数据集都用全训练集**：本地实际 TaxiBJ 512/2491、BikeNYC 511/511、CHAP 512/2626。
- 三个 seed 使用相同的训练窗口与离线缺失掩码，只改变训练随机性，不代表三套独立缺失模式。
- random CSV 与抽取后的 NPZ 行严格对齐；fixed 保留原一行空间时间掩码。
- 验证/测试集完整使用；不同候选使用相同 split、掩码、优化器和预算。
- 每个运行只保留一个验证最优 best.pt；更优时覆盖，最终重载测试一次。
- 重新训练 B00/B01，不将历史 80 epoch 的成绩混入当前 120 epoch 主对照。

本轮优先覆盖跨数据集与种子稳定性，**不能据此声称所有缺失率或全训练数据预算都已验证**。如新结构有效，下一步再固定方案扩展到 0.2/0.6/0.8 和完整训练集，而不是根据本轮 test 反复调参。

## 4. 执行

在项目内层目录运行，不需要启动第二张 GPU：

```bash
conda activate difftdi
python scripts/run_scale_completion_experiments.py \
  --gpu 0 \
  --deadline "2026-09-10 09:00"
```

策略文件：`configs/presets/scale_completion_experiments.json`。所有实验共用的 epoch、验证间隔、batch、窗口数、种子，以及候选结构/损失差异都在 JSON 中控制；不要针对单个候选缩短 epoch。

执行顺序：先 seed=42 的六个条件、每条件七个方案，再 seed=2026 的三主方案六条件，最后 seed=3407 的三主方案六条件。所有任务单进程、单卡串行，避免双卡同时高负载。

正式启动前会测量七方案×三数据集的短批次训练/验证速度。测时参数会丢弃，不会作为正式训练的初始权重，不访问测试指标；仅读取测试集长度估算评估耗时。

2026-09-09 22:28 左右的 GPU0 RTX 3090 实测投影：全队列约 **8.45 小时（包含 1.6 倍余量及每次启动 30 秒）**，当时预计次日 06:55 完成。这不是保证；CPU/I/O 争用、其他 GPU 任务、热降频、服务器宕机或晚启动都会影响结束时间。

`--deadline` 使用北京时间，与服务器本地时区无关：若开始前预计整个队列超时，则不启动正式实验；队列中若下一任务预计越界，则停止新增任务，不杀正在运行的训练、不偷偷截断 epoch。不会自动缩短某个方案或把不完整实验记作成功。

其他命令：

```bash
# 只查看 78 个任务，不生成训练结果
python scripts/run_scale_completion_experiments.py --dry-run

# 仅重新测时，不启动正式队列
python scripts/run_scale_completion_experiments.py --gpu 0 --calibrate

# 中断后原命令重跑，跳过本协议下已经完整训练、验证和测试的任务
# 若已过原截止时间，需要更新 --deadline 或去掉它
python scripts/run_scale_completion_experiments.py --gpu 0

# 只汇总，不训练
python scripts/run_scale_completion_experiments.py --summary-only
```

跳过要求：配置一致、所有 epoch 完成、验证频率完整、训练/验证 MAE/RMSE/loss 有限、最佳 epoch 匹配、测试 MAE/RMSE 有限、结束标志和 best.pt 存在。失败任务重跑，从头训练，不把 best.pt 当作完整断点恢复状态。

## 5. 输出与分析方法

统一放在 `outputs/v23/scale_completion/comparison/<协议指纹>/`：

- `protocol.json`：配置、源码哈希、源数据文件状态；配置/代码/源文件状态改变会产生新协议目录。运行中不要改源码或数据。
- `configs/`、`data/`：每任务配置和同源训练子集/选择索引。
- `runs/`：按数据集、候选及种子、缺失模式组织运行。每次含 config.json、唯一 best.pt、train.log、val.log、test.log、metrics.jsonl。
- `logs/`：各任务原始控制台输出；终端实时显示紧凑 epoch 信息与错误。
- `timing.json`：分模型、分数据集的参数量与耗时估计。
- `summary.csv`、`summary.json`：78 组状态、最佳轮次、验证 MAE、测试 MAE/RMSE；JSON 还包含最佳验证及最终测试的完整诊断指标。
- `comparison.json`：逐数据集/模式的种子均值、样本标准差，以及同条件同 seed 的百分比变化；负数为改善。未完成组明确标记完成数，单 seed 不伪造标准差。

建议依次判断：

1. **先验收有效性**：78/78 完成、无非有限值、选优流程正常、末轮是否仍大量刷新最佳。
2. **主效果看验证集**：B01−B00 判断监督贡献，N01−B01 判断新参数化贡献。分别列六条件的均值±标准差与三个 seed 的配对方向；三种子只是初步稳定性证据，不直接宣称统计显著。
3. **再看测试集一致性**：是否与验证改善同方向，有无少数数据集明显退化。不要直接把不同单位的三个数据集 MAE 相加取平均。
4. **机制分析**：检查分支 MAE、completion gate 使用率、normalized_correction_abs_mean、residual_saturation_fraction。饱和率长期高且 NB2 验证更好才支持“边界太紧”；NU 接近 N01 说明当前动态路由可能冗余；NG 以显著更低成本接近 N01 则支持更简单聚合，但需追加多种子确认。
5. **避免过度归因**：消融只有 seed42，不能据微小差距定论；不能仅凭修正幅度减少就认定精度提升。若最佳轮次集中 120，下一步给全部主对照同样延长预算，不只延长喜欢的候选。
