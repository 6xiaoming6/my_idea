# V17-single 探索性消融实验详细执行方案

> 适用分支：`v17-single`  
> 实验目的：在继续设计下一版本之前，先确定 V17 中哪些组件真正带来收益、哪些组件造成 TaxiBJ fixed 和 CHAP 退化。  
> 实验性质：**探索性机制诊断**，不是论文最终消融表。  
> 核心原则：一次只改变一个因素，先用少量代表点筛选，再对关键结论补多随机种子。

---

# 1. 为什么必须先做探索性消融

V17 的完整结果呈现出非常明显的“局部成功、整体不稳”：

- 相对 Main：10/24 个点更好，但 24 点平均 MAE 仍退化约 1.11%；
- TaxiBJ random@0.4 取得当前六版本最好结果；
- BikeNYC fixed@0.8 取得当前六版本最好结果；
- TaxiBJ fixed 明显不如 V16；
- CHAP fixed/random 均明显不如 V16；
- TaxiBJ 尺度权重接近 Fine 单尺度；
- CHAP 部分实验三个尺度几乎同时选择同一个专家；
- TaxiBJ 的 Routed Branch Gate 接近 0.95，近似常开；
- V17 尚未进行自身组件消融。

因此，当前不能直接判断：

```text
V17 的成功来自：
Scale Adapter？
Hierarchical Router？
Fine-preserved Parallel Fusion？
Fine Floor？
Sample-wise Route Gate？
Shared/Routed 统一尺度权重？

V17 的失败又来自：
Router 过度统一？
Fine Floor 放大 Fine 偏置？
Shared 和 Routed 共用尺度权重？
专家同步塌缩？
Route Gate 饱和？
```

如果不先把这些问题拆开，直接设计新版本会再次把多个因素混在一起，无法判断改进是否真正有效。

# 2. 探索性消融的目标

本轮实验只回答五个问题。

## Q1：Scale Adapter 是否真正有效

V17 在 Fine、Mid、Coarse 三个尺度进入共享专家池前，分别增加了零初始化的 `64→16→64` Adapter。

需要回答：

```text
Adapter 是否改善了跨尺度共享专家的适配能力？
还是只增加了额外自由度并引发过拟合？
```

## Q2：统一 Hierarchical Router 是否优于解耦路由

V17 使用一个全局多尺度上下文，同时输出：

```text
尺度权重
每尺度专家权重
Routed Branch Gate
```

需要回答：

```text
尺度和专家联合决策是否有效？
还是因为过度耦合导致三个尺度选择相同专家？
```

## Q3：Fine-preserved Parallel Fusion 是否是突破点来源

V17 将 Main 的：

```text
Coarse → Mid → Fine
```

改为：

```text
Fine / Mid / Coarse 直接并行融合到 Fine
```

需要回答：

```text
TaxiBJ random@0.4 和 BikeNYC fixed@0.8 的收益是否主要来自并行融合？
CHAP 是否更需要原来的层次渐进融合？
```

## Q4：Fine Floor 是否造成 TaxiBJ fixed 的 Fine 塌缩

当前：

```text
w_safe = 0.75 * w_router + 0.25 * [1,0,0]
```

该形式不仅保证 Fine 不低于 0.25，还会继续抬高已经很高的 Fine 权重。

需要回答：

```text
Fine Floor 是否保护了 random 场景？
是否同时伤害 fixed 场景？
```

## Q5：Sample-wise Route Gate 和统一尺度权重是否过度耦合双分支

当前 Shared 和 Routed 使用同一套尺度权重，Routed Gate 在 TaxiBJ 上接近常开。

需要回答：

```text
样本级 Route Gate 是否优于 Main 的全局 route_gamma？
Shared/Routed 是否应该继续共用一套尺度权重？
```

# 8. E2：Decoupled Expert Router

## 8.1 目的

单独验证“统一专家路由”是否导致 CHAP 三尺度同步选择同一专家。

## 8.2 修改原则

保留 V17 的：

```text
Scale Router
scale_weight
route_branch_gate
Fine-preserved Fusion
```

只将专家路由改回 Main 的三个独立 `QualityRouter`：

```python
gate_f = self.router_f(h_f, q_f, scale_id=0)
gate_m = self.router_m(h_m, q_m, scale_id=1)
gate_c = self.router_c(h_c, q_c, scale_id=2)
```

不要同时恢复 Main Scale Gate，否则会混入两个变量。

## 8.3 配置

```json
{
  "model": {
    "v17": {
      "expert_router_mode": "decoupled"
    }
  }
}
```

支持：

```text
hierarchical_shared_head
decoupled
```

## 8.4 判断逻辑

### 若 CHAP 明显改善

且出现：

```text
三个尺度专家分布差异增大
有效专家数增加
Top-2 第二专家权重上升
```

说明当前共享 Expert Head 过度耦合，应在后续版本中改成：

```text
共享基础 Logit + 每尺度轻量 Offset
```

### 若 Taxi random@0.4 明显退化

说明统一专家上下文可能是该成功点的重要来源，后续不能完全拆回三个独立 Router，应采用软耦合方案。

## 8.5 核心诊断

```text
expert_entropy_f/m/c
expert_top1_frequency_f/m/c
effective_expert_count = exp(entropy)
top2_second_weight
cross_scale_expert_agreement
```

`cross_scale_expert_agreement`：

```text
三个尺度 Top-1 专家相同的样本比例
```

## 9.1 目的

验证 V17 的并行尺度融合是否是成功点的主要来源，以及 CHAP 是否更适合层次渐进传播。

## 9.2 修改

保留：

```text

Hierarchical Router

```

只将 Routed Fusion 从：


```text

```


## 9.3 判断逻辑

### 若 P1、P2 明显退化

说明并行融合是 V17 突破点的重要来源。

### 若 P4 CHAP 明显改善

说明环境场更适合层次式传播，未来可能需要：

```text
Shared 分支渐进融合
```

而不是全部统一成并行。

# 11. E5：Hard Fine Floor

## 11.1 为什么需要单独测试

当前线性混合会无条件增加 Fine 权重。

Hard Floor 只在 Fine 权重低于阈值时调整：

```text
若 w_f >= floor：
保持原权重。

若 w_f < floor：
将 w_f 提升到 floor，
其余 active scale 按原比例缩小。
```

## 11.2 推荐实现

```python
def apply_hard_fine_floor(
    weight: torch.Tensor,
    fine_floor: float,
    eps: float = 1e-6,
) -> torch.Tensor:
    w_f = weight[:, :1]
    w_other = weight[:, 1:]

    need_raise = w_f < fine_floor

    other_sum = w_other.sum(
        dim=1,
        keepdim=True,
    ).clamp_min(eps)

    target_other_sum = 1.0 - fine_floor
    scaled_other = (
        w_other
        / other_sum
        * target_other_sum
    )

    floored = torch.cat(
        [
            torch.full_like(w_f, fine_floor),
            scaled_other,
        ],
        dim=1,
    )

    return torch.where(
        need_raise,
        floored,
        weight,
    )
```

## 11.3 判断逻辑

若 Hard Floor：

```text
保留 P1/P2；
改善 P3；
不损害 P4；
```

则它应替代当前线性 Fine Floor。

# 12. E6：Global Route Gamma

## 12.1 修改

关闭 Hierarchical Router 的 `route_branch_gate`，恢复 Main：

```python
gamma = torch.sigmoid(self.route_gamma)
h_main = h_shared + gamma * h_route_proj
```

其余全部保持 V17。

## 12.2 目的

判断 TaxiBJ 上接近 0.95 的样本级 Route Gate 是否造成 Routed 分支常开。

## 12.3 两种实现方式

### 方式 A：可学习全局 Gamma

与 Main 一致：

```text
route_gamma_init = -3
```

### 方式 B：冻结为 Main 初始值

探索阶段不推荐，因为过于保守。优先使用方式 A。

## 12.4 判断逻辑

### 若 P3/P4 改善且 P1/P2 基本保持

说明样本级 Gate 没有真正提供样本区分，反而引发饱和，应恢复全局 Gamma 或改成小范围调节。

### 若 P1/P2 明显退化

说明动态 Branch Gate 是成功点的一部分，但需要增加饱和控制，而不是删除。

## 12.5 诊断

```text
route_gate_mean/std
route_gate_saturation_high = mean(gate > 0.9)
route_gate_saturation_low  = mean(gate < 0.1)
```

# 13. E7：Independent Shared Scale Gate

## 13.1 这是最重要的结构诊断

V17 当前让 Shared 和 Routed 使用完全相同的尺度权重。

E7 改为：

```text
Routed：
继续使用 Hierarchical Router 的 scale_weight。

Shared：
恢复 GatedCrossScaleSharedExpert 内部
ReliabilityAwareScaleGate。
```

专家 Router、并行 Routed Fusion、Route Gate 均不变。

## 13.2 配置

```json
{
  "model": {
    "v17": {
      "unified_scale_weight": false
    }
  }
}
```

当前仓库中该配置项存在但没有实际接入，应在探索分支中真正实现。

## 13.3 目的

验证：

```text
完全统一尺度权重
是否削弱 Shared/Routed 的互补性。
```

预期语义：

```text
Shared：
稳定、可靠性驱动、公共跨尺度信息。

Routed：
难度驱动、样本自适应专家信息。
```

## 13.4 判断逻辑

### 若 P3/P4 明显改善

同时 P1/P2 基本保持，说明下一版本最优方向是：

```text
双尺度 Gate 软耦合
```

而不是继续使用完全统一尺度权重。

### 若所有点退化

说明共享尺度决策的一致性确实重要，应保留统一 Gate。

## 13.5 必须记录

```text
shared_scale_weight
routed_scale_weight
两者 L1 距离
两者 cosine similarity
```

# 15. 第一阶段结果判定规则

## 15.1 明确有效

某组件被删除后满足：

```text
至少 2 个点退化 >2%
且没有失败点改善 >3%
```

则认为该组件具有明确正贡献。

## 15.2 明确有害

某组件被删除或替换后满足：

```text
失败点改善 >3%
成功点退化 <=1.5%
```

则认为 Full V17 当前实现有害，应优先修改。

## 15.3 模式依赖

满足：

```text
成功点退化 >2%
失败点改善 >3%
```

说明该组件不是简单保留/删除问题，而应做条件化或软耦合。

## 15.4 结果不明确

所有变化均小于：

```text
1%
```

单 seed 下视为不确定，进入第二阶段多 seed 验证。

# 16. 第二阶段：针对性组合实验

第一阶段结束后，只允许组合已经有证据支持的修改。

不要直接把所有“看起来更好”的修改一次性叠加。

## 16.1 推荐候选组合

### C1：Soft-Decoupled Scale Fusion

当 E7 有效时：

```text
Shared 使用独立可靠性 Scale Gate
```

不增加一致性 Loss，先验证纯解耦。

### C2：Hard Fine Floor

当 E5 优于 E0/E4 时，替换线性 Fine Floor。

```text
gate = clamp(
```

这已经属于下一版本候选，不应在第一阶段实现。

# 17. 第二阶段多随机种子

只对以下版本补 3 seed：

# 18. 路由诊断指标

仅比较 MAE 无法解释机制，必须同步保存以下指标。

## 18.1 Scale 指标

```text
scale_weight_f/m/c mean
scale_weight_f/m/c std
scale_entropy
effective_scale_count = exp(scale_entropy)
scale_top1_frequency
```

## 18.2 Expert 指标

每尺度：

```text
expert_entropy
effective_expert_count = exp(expert_entropy)
expert_top1_frequency
top2_first_weight
top2_second_weight
top2_weight_ratio
```

`top2_second_weight` 特别重要，用于判断形式上的 Top-2 是否已退化为 Top-1。

## 18.3 跨尺度专家一致性

```text
same_top1_all_scales_rate
same_top1_fine_mid_rate
same_top1_mid_coarse_rate
```

CHAP 若这些比例接近 1，说明专家同步塌缩。

## 18.4 Branch 指标

```text
route_gate_mean/std
route_gate_high_saturation
route_gate_low_saturation
shared_feature_rms
routed_feature_rms
effective_routed_ratio =
    RMS(gate * routed_feature)
    / RMS(shared_feature)
```

## 18.5 Adapter 指标

```text
adapter_delta_rms
adapter_relative_rms
```

## 19.1 塌缩判定建议

### Scale Collapse

```text

且 scale entropy < 0.2
```

### Expert Collapse

```text

或 effective expert count < 1.3
```

### Route Gate Saturation

```text
mean gate > 0.90
且 std < 0.03
```

这些阈值仅用于探索诊断，不应作为训练硬约束。

# 24. 探索完成后的决策树

## 情况 A：E7 Independent Shared Scale 最有效

说明：

```text
V17 最大问题是 Shared/Routed 过度统一。
```

下一版本应采用：

```text
稳定 Shared Scale Gate
+
动态 Routed Scale-Expert Router
+
轻量一致性约束或无约束
```

这是最优先的候选方向。

## 情况 B：E5 Hard Fine Floor 最有效

说明：

```text
Fine 保留思想正确，
但线性 Fine Floor 实现不合理。
```

下一版本只替换 Floor，不改 Router 主体。

## 情况 C：E2 Decoupled Expert Router 明显修复 CHAP

说明：

```text
共享 Expert Head 导致跨尺度同步塌缩。
```

下一版本采用：

```text
共享基础专家 Logit
+
每尺度轻量 Offset
```

而不是完全独立的大 Router。

## 情况 D：E3 Progressive Fusion 修复 CHAP，但伤害 P1/P2

说明融合具有数据依赖：

```text
Shared 分支使用 Progressive
Routed 分支使用 Parallel
```

比统一一种 Fusion 更合理。

## 情况 E：E6 Global Route Gamma 更稳定

说明样本级 Route Gate 没有形成有效区分。

下一版本优先恢复全局 Gamma，不要继续给 Gate 增加输入。

## 情况 F：E1 No Adapter 基本不变

删除 Adapter，减少结构和参数。

# 28. 最终建议

本轮探索的重点不是“把 Full V17 做得更复杂”，而是确定：

```text
TaxiBJ random@0.4 的突破来自哪个组件；
BikeNYC fixed@0.8 的突破来自哪个组件；
TaxiBJ fixed 的退化由 Fine Floor、Route Gate
还是统一尺度权重造成；
CHAP 的退化由专家同步塌缩
还是并行融合造成。
```

最值得优先验证的三个消融是：

```text
1. Independent Shared Scale Gate
2. Hard Fine Floor
3. Global Route Gamma
```

如果这三项能够在保留 P1/P2 的同时改善 P3/P4，下一版本就应该围绕：

```text
稳定 Shared 多尺度路径
+
动态 Routed Scale-Expert 路径
+
软耦合而非完全统一
```

进行设计。
